# 氿悦体育独立站开发、测试与发布体系设计

日期：2026-09-08  
状态：已完成方案讨论，待用户审核书面设计

## 1. 背景与目标

当前仓库实际承载的是氿悦体育单店官网生产程序，而不是仓库名称所暗示的 Neon Tides 项目。现有系统由原生 HTML、CSS、JavaScript、单文件 Node.js HTTP 服务和 JSON 数据文件构成，提供官网展示、预约询盘、经同意的访问统计和单管理员后台。

本次改造目标是把它建设成适合单店长期稳定运行、易于维护、可测试、可审计和可回滚的生产系统。业务规模按单实例、低到中等访问量设计，不建设多租户、微服务、复杂权限或高可用集群。

已确认的关键决策：

- 采用渐进式工程化改造，不重写现有网站视觉和业务；
- 正式环境采用 Linux、Docker Compose 和 Caddy；
- 数据从 JSON 文件迁移到 SQLite；
- GitHub Actions 负责测试、构建、预发布和生产发布；
- 生产发布需要人工批准；
- 使用独立测试子域名作为预发布环境。

## 2. 范围与非目标

### 2.1 本次范围

- 修复仓库基线，恢复缺失的开发与配置文件；
- 拆分单文件后端，建立清晰模块边界；
- 将预约、统计、会话、迁移状态和必要审计数据迁移到 SQLite；
- 建立本地开发、自动测试、镜像构建、预发布和生产发布流程；
- 建立备份、恢复、监控、日志和回滚机制；
- 保持现有公开页面、预约流程、统计同意和后台功能可用。

### 2.2 非目标

- 不引入微服务或 Kubernetes；
- 不引入 React、Vue 等前端框架；
- 不建设多门店、多租户或多角色权限系统；
- 不接入支付、会员、短信、邮件、微信或 CRM；
- 不通过增加复杂基础设施来解决当前规模不存在的问题。

## 3. 目标架构

```text
访客或管理员浏览器
        │ HTTPS
        ▼
Caddy
├─ 自动申请和续期证书
├─ 统一安全响应头
└─ 反向代理
        │
        ▼
Node.js 单体应用
├─ routes         HTTP 路由与响应适配
├─ services       预约、统计和认证业务
├─ repositories   SQLite 数据访问
├─ middleware     登录、CSRF、限流和输入校验
├─ config         环境配置与启动检查
├─ db             连接、迁移和事务
└─ public         原生前端资源
        │
        ▼
SQLite
├─ inquiries
├─ analytics_events
├─ admin_sessions
├─ schema_migrations
└─ audit_logs
```

系统保持一个应用容器和一个 Caddy 容器。Node.js 应用只运行一个实例，以符合 SQLite 和单店业务规模。应用端口不直接暴露公网，仅由 Caddy 访问。

## 4. 应用组件与边界

建议的源码结构：

```text
src/
├─ server.mjs
├─ app.mjs
├─ config/
├─ routes/
├─ services/
├─ repositories/
├─ middleware/
└─ db/
   ├─ migrations/
   └─ migrate.mjs
public/
tests/
├─ unit/
├─ integration/
├─ e2e/
└─ fixtures/
deploy/
docs/
.github/workflows/
```

各层职责如下：

- `server.mjs`：创建 HTTP 服务、监听端口和处理优雅退出；
- `app.mjs`：组合路由、中间件和依赖，便于集成测试直接启动应用；
- `routes`：解析 HTTP 请求并将结果转换为 HTTP 响应，不包含数据库细节；
- `services`：实现预约、统计、认证、数据保留等业务规则；
- `repositories`：封装 SQL 和事务，使业务层不依赖表结构细节；
- `middleware`：实现认证、CSRF、请求 ID、限流、输入 Schema 校验和统一错误转换；
- `db`：负责 SQLite 连接配置、迁移、健康检查、备份协调和事务入口；
- `public`：继续使用无构建步骤的原生前端。

## 5. 数据设计

SQLite 启用 WAL、外键约束和合理的 busy timeout。所有结构变化通过版本化迁移完成，应用启动时先检查并执行允许的迁移；迁移失败时拒绝启动。

主要数据表：

- `inquiries`：预约内容、状态、创建和更新时间、隐私告知版本、是否允许统计归因；
- `analytics_events`：经同意产生的页面访问和内容互动事件；
- `admin_sessions`：会话令牌摘要、CSRF 相关信息、创建时间和过期时间；
- `schema_migrations`：已执行迁移版本和执行时间；
- `audit_logs`：后台的重要状态变化和删除动作，不保存已删除的个人信息正文。

预约使用即时事务提交，只有事务成功后才能向用户显示提交成功。统计事件可以批量写入；统计失败不阻断官网使用。事件和过期会话由定时维护任务清理。

从现有 JSON 迁移时，提供一次性、可重复验证的导入工具。迁移前生成备份，导入完成后核对记录数量和关键字段；生产切换经过验证后，旧 JSON 只作为受保护的迁移备份保留，不再双写。

## 6. 开发模式与仓库治理

采用短分支和 Pull Request：

1. `main` 始终保持可发布；
2. 每项工作从 `main` 创建短期功能或修复分支；
3. 功能和缺陷修复先建立失败测试，再实现；
4. Pull Request 自动执行全部质量门禁；
5. 通过自动检查和审查后合并；
6. 合并 `main` 自动部署预发布；
7. 预发布验证通过后人工批准生产发布。

本地开发使用 Docker Compose 和独立 SQLite 数据库。Node.js 使用 `--watch` 提供后端自动重启，前端继续直接加载静态文件，不增加前端打包链。

仓库必须包含：

- 可安全提交的 `.env.example`；
- 排除密钥、数据库、备份和日志的 `.gitignore`；
- 锁定依赖版本的 `package-lock.json`；
- 统一的开发、检查、测试、迁移和启动脚本；
- 与 CI 和容器一致的 Node.js LTS 主版本约束；
- 清晰的贡献、部署、回滚和恢复说明。

代码格式和基础静态检查使用 Prettier 与 ESLint，但不引入与当前规模不匹配的重型工具。

## 7. 测试体系

### 7.1 基线修复

首先恢复 `.gitignore` 和 `.env.example`，让现有六项测试全部通过，再开始结构性改造。任何既有失败必须先归类，避免将原有缺陷误判为重构回归。

### 7.2 单元测试

覆盖配置校验、输入规范化、密码校验、统计聚合、时区换算、数据保留策略和错误映射等纯逻辑。单元测试必须快速且互不共享状态。

### 7.3 集成测试

使用临时 SQLite 数据库启动真实应用，覆盖：

- 预约创建、读取、更新状态和删除；
- SQLite 事务、约束和迁移；
- 登录、退出、过期和服务重启后的会话；
- CSRF、防跨站写入、请求体限制和接口限流；
- 统计同意、拒绝和来源归因边界；
- 数据库不可写、内容损坏或迁移失败时的行为。

### 7.4 端到端测试

使用 Playwright 在桌面和移动视口验证：

- 官网、隐私页、媒体资源和主要导航；
- 同意或拒绝统计后的行为；
- 图片画廊和预约表单；
- 管理员登录、处理和删除预约；
- 关键页面无 JavaScript 错误、失败请求和资源 404；
- 基础可访问性和关键页面截图。

### 7.5 部署与恢复测试

对最终 Docker 镜像验证容器健康检查、全新数据库初始化、旧数据库迁移、备份与恢复、Caddy 反向代理以及预发布线上冒烟流程。

## 8. CI/CD 与环境

Pull Request 流程：

```text
格式与静态检查
→ 单元测试
→ 集成测试
→ Playwright 端到端测试
→ Docker 镜像构建
→ 镜像安全扫描
```

合并 `main` 后：

```text
构建正式镜像
→ 使用 Git commit SHA 标记
→ 推送 GitHub Container Registry
→ 自动部署 staging
→ 执行迁移和线上冒烟测试
→ 等待 production Environment 人工批准
→ 生产数据库备份
→ 部署同一个镜像
→ 迁移、健康检查和生产冒烟测试
```

预发布与生产环境使用独立域名、容器、SQLite 数据库、数据卷和密钥。预发布只使用虚构测试数据，禁止复制生产预约数据。

服务器只拉取并运行已经构建的镜像，不在生产服务器上拉源码或现场构建。镜像以 commit SHA 作为不可变版本标识，旧版本保留以支持回滚。

GitHub `staging` 和 `production` Environment 分别保存部署凭据。生产环境设置人工审批。管理员密码哈希、会话密钥、SSH 私钥和其他凭据不得进入 Git 仓库、构建日志或镜像层。

## 9. 发布与回滚

发布前自动创建 SQLite 一致性备份。应用、迁移或健康检查失败时停止发布并切回上一镜像。

数据库迁移遵循向前兼容原则。删除字段、改变含义等破坏性变化采用扩展—迁移—收缩的多次发布方式，确保旧版本应用在回滚期间仍能读取数据库。

每次发布记录：

- Git commit SHA 和镜像摘要；
- 数据库迁移版本；
- 部署时间和审批人；
- 健康检查与冒烟测试结果；
- 回滚目标版本。

## 10. 备份、监控与日志

- 每日执行 SQLite 在线备份并生成 SHA-256；
- 至少一份备份复制到服务器之外的受控存储；
- 自动检查备份完整性，每月执行实际恢复演练；
- 监控首页、健康接口、数据库读写、磁盘空间、容器重启、证书期限和备份结果；
- 正常运行保持安静，仅在故障或需要人工处理时通知；
- 使用结构化 JSON 日志和请求 ID；
- 日志不得记录密码、会话 Cookie、完整电话、预约正文或其他不必要的个人信息；
- 制定日志、统计事件、预约数据和备份各自的保留期限。

健康检查区分进程存活与依赖就绪。数据库无法正常读写时，就绪检查失败，阻止错误实例继续接收生产流量。

## 11. 安全与隐私

- 后台保持单管理员模型；
- 管理密码继续使用 Node.js 内置 scrypt，只保存带随机盐的哈希；
- 会话存入 SQLite，Cookie 使用 `HttpOnly`、`Secure` 和 `SameSite=Strict`；
- 所有后台写操作验证 CSRF Token；
- 登录、预约和统计接口使用独立限流策略；
- 只信任由 Caddy 覆盖的代理来源信息；
- 请求体使用结构化 Schema 验证；
- 容器以非 root 用户、只读根文件系统和最小权限运行；
- Node.js、依赖、GitHub Actions 和基础镜像固定版本并定期更新；
- 构建后的镜像执行漏洞扫描。

预约信息处理同意与访问统计同意保持独立。拒绝统计时不创建或保存统计访客标识。后台默认遮掩部分电话号码；删除预约后只保留不含个人信息的必要审计记录。预发布环境不得使用生产个人信息。

## 12. 错误处理

- API 使用稳定的机器错误码和用户可读中文提示；
- 生产响应不暴露堆栈、SQL 或本机路径；
- 内部日志包含请求 ID、错误类型和必要上下文，但排除敏感字段；
- 预约事务失败时明确提示失败，不得返回虚假成功；
- 统计写入失败不影响页面和预约，但必须产生可监控记录；
- 数据库迁移失败时应用拒绝启动；
- 前端处理网络中断、超时和重复提交，并展示明确状态。

## 13. 实施阶段

本设计后续拆分为顺序实施计划：

1. 修复仓库与测试基线；
2. 建立模块化应用骨架，保持现有行为；
3. 引入 SQLite、迁移系统和 JSON 导入工具；
4. 迁移预约、统计、会话与审计；
5. 完成测试分层与浏览器测试；
6. 完成开发和生产 Docker 配置；
7. 建立 GitHub Actions、GHCR、预发布和人工批准生产发布；
8. 建立备份、恢复、监控、日志和运维文档；
9. 在预发布完成全链路演练后切换生产。

每个阶段都必须保持测试通过并形成可回滚提交。生产迁移前必须完成备份恢复演练和旧数据导入核对。

## 14. 验收标准

- 新开发者可仅根据文档启动本地环境并运行全部测试；
- 所有当前业务功能在改造后保持可用；
- Pull Request 未通过质量门禁时无法合并；
- `main` 合并后自动部署预发布，生产发布必须人工批准；
- 预发布和生产运行相同镜像摘要；
- 生产应用端口不直接暴露公网；
- SQLite 迁移、备份、恢复和回滚流程均经过自动或人工演练；
- 服务重启后预约数据和有效管理员会话仍存在；
- staging 不包含生产个人信息；
- 敏感信息不进入仓库、镜像或日志；
- 健康检查、磁盘、证书、容器和备份故障能够触发通知；
- 运维人员可以依据文档恢复数据并回滚到上一版本。
